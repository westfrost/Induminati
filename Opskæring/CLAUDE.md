## 1. Purpose

Solves the "how do we cut this order's belts out of the mother rolls we have" problem for conveyor-belt production. Input is a set of one or more mother rolls (stock rolls, each with a width and length) and a set of belt orders (each a width × length × quantity). The tool computes a cutting plan — which rolls to use, how many transverse cuts and how many longitudinal strips per cut, and which belts (or "dorn" bundles of belts) come out of each strip — that minimizes wasted roll length/area, and produces both an on-screen visual/tabular plan and a printable A4 work order ("arbejdsseddel") that a machine operator follows at the cutting table.

## 3. Core algorithm

**Model: three-stage guillotine cutting**, matching the physical process exactly (a comment above the engine makes this explicit):
1. **Tværsnit** (transverse cut) — cut a full-width **row/section** off the mother roll at some length H.
2. **Længdesnit** (longitudinal cut) — slit that row into side-by-side **strips** (columns) of various widths.
3. **Tværsnit** — cut each strip into its individual belts (or a dorn bundle, later slit into N identical belts).

Rolls are consumed strictly in the order entered; within a roll, sections are appended end-to-end until the roll runs out or nothing more fits.

**Strategy parameter `S` (since 24-09-2026).** Every engine function (`fillColumn`, `fillSection`, `bestSection`, `placePass`, `attemptPlan`, `planCutting`) takes a strategy object `S`. The frozen default **`GRUND`** reproduces the v3.6 algorithm described in Steps 0–6b *exactly* — verified plan-for-plan (identical sections, strips, items, remnants) against a frozen copy of the v3.6 engine on 400 random orders before shipping. All the other `S` fields (`exact`, `rowDP`, `alpha`, `beta`, `noise`, `candLimit`, `lookahead`, `frieH`, `subsetMerge`) are only ever switched on by the optimizer (§3b); `vaelgRullerFraLager` and any call that omits `S` get `GRUND`. **The whole engine (units → optimizer) lives between the markers `// ---- MOTOR START ----` and `// ---- MOTOR SLUT ----` and must stay DOM-free** — `motortest.js` extracts exactly that block and runs it in Node (it only needs `EPS`, which it defines itself).

**Step 0 — "units" (`buildUnits`).** Belt line items are grouped by (width, length). For each group, if dorn packing is on, `qty ≥ 2`, and `length ≤ dorn.maxL`, it computes `perDorn = floor((dorn.maxW - dorn.tillaeg) / width)`; if `perDorn ≥ 2` the group's belts are split into dorn bundles ("units" of kind `'dorn'`) sized as evenly as possible across `ceil(qty/perDorn)` bundles (avoids one bundle ending up with a single leftover belt — e.g. splits 10 into 5+5, not 6+4). Groups that don't qualify become individual `'band'` units. Every unit carries `w` (width), `len` (cut length = original length + buffer), and a `bands` array (the underlying real belts it represents) — a dorn unit's `bands` array has N entries so the work order can always say "cut this strip into N belts of width W." `explodeUnit()` reverses a dorn back into individual band units when the dorn can't be placed (too wide/long for any roll, or gets rejected by the retry logic below).

**Step 1 — filling one row (`fillSection`).** Given a target row width B and row length cap H: units are bucketed by width (`byW`), each bucket sorted longest-first. Repeatedly picks, among all widths that still fit in remaining width `wRem` (and haven't hit `maxPerWidth` count), the width whose next strip (`fillColumn`) can be packed with the greatest filled length — because "area gained per unit of roll width consumed" equals the filled length for a fixed row length H. `fillColumn` greedily packs units end-to-end into a single strip, longest available unit first, without exceeding cap H. Resulting strips (columns) are sorted widest-first (ties by fill) so identical widths in a row end up adjacent — keeps knife setups grouped and gives the operator all same-width belts consecutively. The row's actual length is `max` over all strips' filled length (not H) — trailing slack in shorter strips becomes their `rest`.

**Step 2 — choosing row length H (`bestSection` + `candidateLengths`).** Rather than trying arbitrary H values, `candidateLengths` restricts candidates to actual achievable strip lengths: every unit's own `len`, plus subset-sums of repeated unit lengths (bounded search, capped at 4000 partial sums), clipped to `[minH, maxH]` where `minH` is forced to be at least the longest remaining unit's length (so nothing is perpetually deferred) — except under the optimizer's `S.frieH`, which lets rows be shorter than the longest remaining unit (this single freedom was the biggest measured win of the optimizer, see §3b). If more than `CAND_LIMIT` (90) candidates result, it downsamples evenly. For each candidate H, `fillSection` is run and scored by absolute **waste** (`H×B - filled area`); ties go to the *longer* row (more material moved + saves a knife changeover). Lowest-waste (then longest) row wins.

**Step 3 — filling a roll and multiple rolls (`placePass`).** For each roll in listed order, repeatedly calls `bestSection` on the remaining available length and appends the winning section, removing placed units from the pool, until nothing more fits or the pool is empty.

**Step 4 — merging identical-layout rows (`mergeSameLayoutSections`).** After a pass, consecutive/any rows on the same roll that ended up with the exact same set of strip widths are merged into one longer row (strips paired shortest-filled-first to keep the merged row as short as possible) — this never costs extra roll length (`max(a)+max(b) ≥ max(a+b)`) and saves a knife-setup change. `attemptPlan` alternates `placePass` and `mergeSameLayoutSections` up to 3 times (merging can free up length that lets more leftover units be placed).

**Step 5 — retry/backoff on unplaceable dorns (`planCutting`).** If some units are left over (`leftovers`) after `attemptPlan`, the algorithm identifies which dorn groups contain the problem belt sizes, explodes just those dorns back into individual belts, and reruns `attemptPlan` from scratch on the whole unit set (not resuming a half-built plan — comment explains resuming would lock in the very rows that failed). This repeats up to 5 rounds, keeping whichever attempt scores best via `planScore`/`betterPlan` (fewest unplaced belts first, then least total roll length used).

**Step 6 — prefer a long leftover over a wide one (`forlaengSidsteRaekkeForLaengsteRest`, added 15-09-2026, called once from `planCutting` right before it returns the final chosen plan — never during `attemptPlan`/`placePass`, which still need the untouched `roll.usedLen` to know how much roll length remains available for further rows within the same attempt).** Explicit business rule: length matters more than width for whatever is left over — the tool should always end up with the *longest* possible reusable remnant, not the widest. If a roll's *last* row doesn't use the full roll width (`sideRest > 0`) and there's still untouched roll length after it (`roll.len - roll.usedLen > 0`), the row's own length is stretched to reach the roll's physical end instead of stopping at exactly what its own content needs. Concretely, for a 260×20000mm roll with a single 80×8350mm belt (350mm buffer, kaplængde 8700mm): the *old* behaviour cut one row of length 8700mm (exactly what the belt needs) and left the rest of the roll — 260×11300mm — as a separate, untouched, full-width mother roll, with the row's own 180mm-wide `sideRest` (180×8700mm) counted as ordinary waste. The *new* behaviour instead extends that row's length to the full 20000mm: the placed 80mm-wide strip now runs the whole roll length (only the first 8700mm of it is real belt, the remaining 11300mm becomes ordinary `længderest` on that narrow strip, `col.rest` recomputed accordingly), and the previously-wasted 180mm-wide `sideRest` now spans the *same* full 20000mm length and becomes the roll's `Tilbage som moderrulle` — 180×20000mm, narrower but much longer than the old 260×11300mm, and (in this example) it even *reduces* total reported waste, since it converts most of what used to be a short, useless 180×8700mm offcut into a long, genuinely reusable remnant. Only the roll's very *last* row can ever be stretched this way — every earlier row's `sideRest` is already boxed in by the row placed right after it and is unavoidably a short scrap piece, exactly as before.

The result is recorded on the roll object as `roll.langRest = { w, len }` (the real reusable remnant's width/length), and `roll.usedLen` is bumped to `roll.len` (the whole roll now genuinely has a cut running its full length, even though part of that cut's width — `langRest` — is deliberately left uncut further and kept as fresh stock rather than turned into scrap). Everywhere the old, simpler `{ w: roll.w, len: roll.len - roll.usedLen }` leftover used to be shown or summed now instead checks for `roll.langRest` first and falls back to that same old formula when it's absent (i.e. when the last row already used the roll's full width, or there was no tail left to stretch into — see `rollStats`, `renderResult`, `sectionsHTML`, `drawRollCanvas`, `openPrintWindow`, and the history snapshot in `saveToHistory`, all touched by this change). **`rollStats`'s `usedArea` explicitly subtracts `roll.langRest`'s area** from `roll.usedLen * roll.w` before comparing to real net belt area — without that subtraction, the kept remnant would wrongly count as wasted material just because it now sits inside `roll.usedLen` instead of being a separate untouched tail; total roll *length* used is allowed to grow, but reported waste must not. On screen and on the printed arbejdsseddel, the kept remnant is shown in green (`tr.langrest` / "Rest til senere brug — … moderrulle, ikke spild") instead of the ordinary grey/italic `tr.siderest` waste row, and on the canvas visualisation it's drawn as part of the last row itself (green, labelled "Rest …") rather than as a separate fixed-height green band below all the rows — that separate band is skipped entirely when `roll.langRest` is set, so the same leftover is never shown twice.

**Minimum remnant width (`minRestW`, "Min. restbredde", added 24-09-2026 on explicit request).** Before 24-09-2026 the stretch was applied unconditionally, however narrow the kept remnant. Now `forlaengSidsteRaekkeForLaengsteRest(roll, minRestW)` computes the remnant width *after* the Step 6b repacking, and if `minRestW > 0` and that width is `< minRestW`, it does **not** stretch (and does not apply the repacking either, since repacked strips could be longer than the unstretched row): the roll is returned untouched, the narrow `sideRest` stays ordinary short waste, and the roll's tail stays a full-width "Rest som moderrulle". Blank/0 = exactly the old unconditional behaviour. Example: 260×20000 roll, one 80×8350 belt, buffer 350 → the remnant would be 180 mm wide: with Min. restbredde 200 the plan is one 8700 mm row + a 260×11300 tail; with 150 (or blank) it's the stretched 180×20000 remnant as before. Only this stretch decision uses `minRestW` — earlier rows' side rests are always waste anyway, and the full-width tail is always ≥ any sane minimum.

**`forlaengSidsteRaekkeForLaengsteRest` no longer mutates its input (24-09-2026).** It returns a *new* roll object (with a copied last section and copied columns), or the original roll when nothing changes. Reason: the optimizer's lookahead and local search evaluate many finished plans that *share* section objects; mutating the last section in place (as v3.6 did) would corrupt those shared rows. `planCutting` maps its used rolls through it.

**Step 6b — pack the last row's same-width strips into fewer, narrower ones before stretching (`packForMinWidth`, added 17-09-2026, called from inside `forlaengSidsteRaekkeForLaengsteRest`, immediately before it stretches the row).** Found via a real user-reported case: 2 identical belts (400×7030mm, 350mm buffer → 7380mm kaplængde) on a 1250×20000mm roll ended up as **two separate** 400mm-wide strips (one belt each), each stretched to the full 20000mm with 12.620mm of pure længderest waste per strip (10.096.000 mm² total waste), leaving only a 450mm-wide kept remnant. The two belts *could* instead have been cut end-to-end in a single 400mm-wide strip (14.760mm of real content, only 5.240mm of waste after stretching — 2.096.000 mm² total, a ~79% reduction) — which also leaves a much wider, more useful 850mm remnant instead of 450mm. The root cause: `bestSection`'s own row-length search (Step 2) picks whichever row layout has the least waste **for that row in isolation** — and two parallel strips exactly matching each belt's own length (H=7380, zero rest) has *less* row-level waste than one combined strip (H=14760, half the row's width sitting empty for twice the length) — so the greedy search always prefers the parallel layout, with no way to know in advance that this row will later become the stretched last row, where the arithmetic flips: once a row is going to be stretched to the roll's physical end regardless, **every column in it gains the exact same amount of extra længderest** (`roll.len − H`, times that column's own width), so the *only* thing that still matters afterwards is how much total width the row's columns occupy — less width used ⇒ less total waste **and** a wider kept remnant, full stop, regardless of the original row-level waste calculation.

`packForMinWidth(cols, capLen)` flattens the last row's columns back to their underlying units (`col.items`), buckets them by width exactly like `fillSection` does, and greedily bin-packs each width bucket into as few strips as possible (first-fit-decreasing) under a length cap of `capLen = last.len + tail` — i.e. the length the row is *about* to be stretched to, so nothing here can ever produce a physically-too-long strip. `forlaengSidsteRaekkeForLaengsteRest` runs this **unconditionally** on the chosen last row, compares the repacked total width used (`packedWidth`) against the row's existing `widthUsed`, and only swaps in the repacked columns if `packedWidth` is strictly smaller — so a row that can't be compacted any further (e.g. every unit already merged into one strip per width, or all units have different widths) is left completely untouched, byte-for-byte identical to the old behaviour. This is why the single-belt case that originally motivated Step 6 (§3's 260×20000mm/80×8350mm example) is unaffected: there's only one unit, nothing to combine, `packedWidth === widthUsed`, no swap.

Because `capLen` is always ≥ the row's original `H` (the cap every column already fit under), and first-fit-decreasing bin-packing with a larger-or-equal capacity can only need the same or fewer bins per width than it did at the smaller capacity, `packForMinWidth` can never *increase* the column count for any width — so it can never violate `maxPerWidth` (already satisfied by the original packing) and never needs to re-check it. It also can never place fewer units than before (every unit from every existing column is re-placed, none dropped), so `leftovers`/`planScore` are untouched by this step — it only ever rearranges units that were already going to be on this roll's last row into a cheaper column layout for the *same* set of units.

Only the very last row of each roll is touched, for the same reason Step 6 itself only ever touches the last row: every earlier row's `sideRest` is already boxed in by the row placed right after it, so combining strips there wouldn't change anything about later waste — the length-stretch bonus, and the reason to prefer minimum width, only exists for the one row that gets to swallow the rest of the roll's length for free.

**Global constraints respected:** roll width (belt/dorn width ≤ roll width), roll length (cut length ≤ available roll length), `maxPerWidth` (max same-width strips per row), dorn max width/length and kerf allowance. Rolls too narrow/short for a unit are pre-filtered in `bestSection`; units too big for *any* roll are exploded immediately in `attemptPlan`.

Key function map: `buildUnits` (belts→units incl. dorn grouping) → `explodeUnit` (undo dorn) → `fillColumn`/`fillSection` (pack one row) → `candidateLengths`/`bestSection` (pick best row length) → `placePass` (fill all rolls) → `mergeSameLayoutSections` (combine identical rows) → `attemptPlan` (one full pass+merge cycle) → `planCutting` (top-level: retry with dorn splitting, then `forlaengSidsteRaekkeForLaengsteRest` on the final plan — see Step 6; also returns `raw`, the pre-stretch plan, for the optimizer's local search) → `planMetrics`/`cmpMetrics` (score a finished plan) → `optimerOpskaering` (the optimizer generator, §3b) → `calculate()` (UI glue, validation, drives the optimizer in chunks, then `renderResult`). `vaelgRullerFraLager` (see §3a) sits on top of this same stack — it calls `planCutting` repeatedly with different candidate roll sets, it never modifies the packing engine itself.

## 3b. Optimering (`optimerOpskaering`, added 24-09-2026)

Added on the explicit request "Egentlig optimering. Giv den gas". The v3.6 engine is purely greedy: each row is the one that looks best *right now*, with no way to see what that costs later (Step 6b documents one example of that myopia). The optimizer runs the engine many times with different strategies and keeps the best **finished** plan.

**Scoring a finished plan (`planMetrics` → `cmpMetrics`), lexicographic, most important first:**
1. fewest belts that could not be placed (`lost`)
2. fewest mother rolls taken into use (`rolls`)
3. least **waste** area (`waste` = Σ roll area − kept remnant − net belt area; the kept remnant is `roll.langRest` or the untouched full-width tail — exactly what the per-roll "Spild" card shows; net belt area includes the buffer, as everywhere else)
4. fewest rows / transverse cuts (`rows`) — i.e. knife setups
5. fewest strips (`strips`)

Waste differences within `SPILD_TOLERANCE` = 0,2 % of the net belt area count as equal, so a plan with practically the same waste but fewer knife setups wins. Roll order is still fixed by the user — the optimizer never reorders rolls.

**Search (`optimerOpskaering` is a generator).** Iteration 0 is always `planCutting(…, GRUND)` = the v3.6 plan, so **the result can never rank worse than the baseline**. Then:
- the **fixed strategies** in `FASTE_STRATEGIER`, in order: exact strip fill, knapsack row fill, both, waste-ratio scoring (`beta`), prefer wide/narrow strips (`alpha`), more row-length candidates, **lookahead** (K = 3–5), `frieH`, `subsetMerge`, and combinations;
- then **random strategies** (`tilfaeldigStrategi`), part of the time as small perturbations of the best strategy so far, sometimes with **fewer belts per dorn** than the maximum (`dornCap` → `buildUnits`' optional 4th argument; `dornGrupper` lists which groups can be capped);
- and in 50 % of the random iterations **local search** (`omlaegPlan`): keep the best plan's first rows up to a random cut point (taken from `plan.raw`, the *pre-stretch* rows) and re-plan everything after it with a random strategy.

Strategy knobs (all off in `GRUND`):
- `exact` — `fillColumnExact`: bounded branch-and-bound subset-sum that fills a strip as full as possible (e.g. 5000+5000 in a 10000 strip instead of 6000 alone). Its first leaf *is* the longest-first choice, so it's never worse than `fillColumn`. Node cap 4000.
- `rowDP` — `fillRowKnapsack`: per width, fill strips one by one; then choose how many strips of each width by a grouped knapsack over the roll width (integer mm rounded *up*, divided by the widths' gcd to keep the table small). Fixes e.g. greedy taking a 600 strip and then having no room for two 500s in a 1000 roll.
- `alpha` (strip pick score × w^alpha), `beta` (row score = waste / area^beta: 0 = absolute waste as in v3.6, 1 = waste ratio), `noise` (seeded random multiplier on scores), `candLimit` (number of row-length candidates, default 90).
- `lookahead` K — `lookaheadSection`: for each of the K best candidate rows (`bestSection(…, topK)`), finish the whole plan greedily (+ merges + stretch) and pick the row whose *finished* plan scores best.
- `frieH` — rows may be shorter than the longest remaining unit (Step 2).
- `subsetMerge` — `mergeSubsetLayouts`: after the identical-layout merge, also merge a row whose multiset of strip widths is a subset of another row's (its strips are cut end-to-end after the matching strips of the bigger row). Never costs length or waste; saves a transverse cut and a knife setup.

**Levels (`OPT_NIVEAUER`)** — max iterations / time cap: Hurtig 60 / 1,2 s, Normal 300 / 8 s, Grundig 1500 / 20 s. The search also stops early if the plan is provably perfect (minimum possible rolls, zero waste, one row per roll) or after `max(120, iter/2)` iterations without improvement. The time cap is only checked *between* iterations, so one slow iteration (lookahead on a big order) can overshoot slightly.

**Determinism.** All randomness comes from `mulberry32`, seeded by a hash of the inputs (`hashString`) plus the iteration number, so the same input gives the same plan — unless a time cap cuts the search short on a slow machine (fewer variants tried). `_uid` is **not** reset inside the optimizer; only `calculate()` resets it before starting. That's safe because every iteration either reuses the base units or builds its own fresh set, and never mixes units from two different `buildUnits` calls in one plan.

**Driving it from the UI.** `calculate()` creates the generator and calls `gen.next()` in ~40 ms slices via `setTimeout`, updating `#opt-progress` in between, so the page stays responsive. Each yield carries the best plan so far, so **"Stop og vis bedste"** finishes immediately with it (`d.opt.stopped = true`). Starting a new calculation cancels a running one (`_job.cancel`).

**Measured effect** (80–150 random realistic orders from the dev harness / `motortest.js`, fixed seeds): the optimizer beats the baseline on ~70–80 % of orders and places *more belts* on ~20 % of them (orders where the greedy baseline left belts unplaced that actually fit); where lost belts and roll count are equal, total waste drops ~55 % (Hurtig), ~60 % (Normal), ~61 % (Grundig); never worse. Average time ~0,2 s (Hurtig), ~0,5 s (Normal), ~2,5 s (Grundig). Of the individual ideas, `frieH` gave the largest single jump (≈ 48 % → 59 % waste reduction at Normal), then local search, then lookahead.

**Testing.** `node Opskæring/motortest.js [antal=60] [niveau=hurtig]` extracts the engine from `index.html`, generates reproducible random orders, validates every optimized plan physically (strip positions, widths vs. roll width, strip vs. row length, rows vs. roll length, `maxPerWidth`, dorn limits, `minRestW`, every belt accounted for exactly once) and checks it's never worse than the baseline; exits 1 on any failure. The "GRUND equals v3.6" comparison used a frozen copy of the v3.6 engine that is **not** in the repo — if you ever change a `GRUND` code path on purpose, say so in this file.

## 3a. Lagerliste-import og automatisk rullevalg (`vaelgRullerFraLager`)

Added so the operator can feed the tool a stock export instead of (or alongside) typing mother rolls by hand, and have it pick the fewest possible physical rolls needed to complete the current belt order.

**Input format.** An uploaded `.xlsx` (read with the same `xlsx.full.min.js`/SheetJS already used by `Ordrer/` and `Kapacitet/`, loaded from CDN — the only external dependency this page has beyond Google Fonts) is expected to be a Business Central-style export with columns `Kode` (optional), `Beskrivelse` (optional), `Bredde`, and `Længde`. Column matching is by header name (`parseLagerRows`), not position, and any other columns present in the export (`Planlagt disponibel balance`, `Bruttobehov`, `Fastlagt tilgang`, etc.) are ignored entirely — only `Bredde`/`Længde` are required; missing either aborts the whole import with a named-column error instead of silently proceeding.

**Antal is always 1 per row — never derived from any quantity/balance column, by explicit instruction (14-09-2026).** An earlier version computed the physical roll count from BC's `Planlagt disponibel balance` (total m² on hand ÷ one roll's area, rounded) — this was deliberately removed: that column doesn't reliably reflect how many *whole, usable* rolls are actually sitting on the shelf, so trusting it could silently tell the operator to cut from rolls that don't really exist in that quantity. Every row in the uploaded file — regardless of what other columns it has — is now treated as exactly **one** physical roll of that Kode/Bredde/Længde. If the same variant genuinely exists more than once in stock, it must appear as separate rows in the spreadsheet (or the user adds more manually after auto-select). A row with non-positive/non-finite width or length is silently skipped and counted in the status line; there is no other validation.

**Selection algorithm.** Every variant is expanded into `antal` individual roll instances (`{kode, beskrivelse, w, len}`), sorted ascending by area (tie-broken by length, then width, then kode). Two phases, both reusing `buildUnits`/`planCutting` unchanged against the page's *current* belt list, buffer, dorn settings, and `maxPerWidth`:
1. **Single-roll check** — for every instance whose own area is at least the order's total base area (`Σ qty × b × (l+buffer)`, a cheap necessary-but-not-sufficient filter that skips the many too-small candidates without running the packer on them), run `planCutting` with *just that one roll*. The first (smallest, since ascending) instance that leaves zero leftovers wins outright — this is what guarantees a genuine 1-roll solution is found and preferred over combining several smaller ones, whenever one exists.
2. **Incremental growth** — if no single roll suffices, build a pool from empty, always adding the next-smallest remaining instance and re-running `planCutting` **on the whole pool from scratch** each time (same "never resume a half-built plan" principle as `planCutting`'s own retry loop) until it succeeds or the entire stock list is exhausted.

This is a heuristic, not a proof of global-minimum roll count — consistent with the rest of the engine, which is greedy/heuristic throughout (see §6) — but it always finds a true 1-roll solution when one exists, and phase 2 never uses more rolls than the number of additions actually needed to reach feasibility.

**Feasibility short-circuit.** Before running any of the above, the click handler (not the pure function itself) checks every belt line against the *widest*/*longest* single item anywhere in the uploaded stock (mirroring `calculate()`'s own roll-vs-belt validation) and refuses with a specific, immediate error if something is structurally too big for anything on the list — this avoids the pathological case (confirmed by testing against a real 52-variant/974-roll export) where an impossible order would otherwise silently burn through the *entire* stock list one roll at a time (hundreds of `planCutting` calls, still fast in absolute terms — under half a second even in that worst case — but pointless) before reporting the shortfall.

**Wiring into `#roll-list`.** On success, previously auto-added rows (marked via `dataset.lagerKode` on the row element) are removed first — manually-typed rows are matched by *not* having that attribute and are never touched — then the chosen instances are grouped by `kode` (so two distinct stock items that happen to share dimensions still render as two separate, individually-traceable rows) into one row per group with `qty` = count, inserted in the same ascending-size order the search used. Each such row shows a small "Fra lager: `<kode>`" chip (`title` = full `Beskrivelse`) below the normal Antal/Bredde/Længde fields (`.band-row.has-kode` / `.roll-kode` in CSS — the row wraps to a second line only when this chip is present). **Editing a tagged row's Bredde or Længde by hand immediately strips the tag and chip** (an `input` listener in `makeRow`) — the row no longer corresponds exactly to that stock item, so showing its kode would be misleading. The kode/beskrivelse then ride along through the normal calculation path: `readRows()` reads them off `dataset` into each row object, `calculate()` copies them onto `rollDefs`, `attemptPlan` copies them onto its `roll` objects, and `renderResult`/`openPrintWindow`/the "urørte moderruller" list all append `· <kode>` to the roll header when present — so an operator reading the printed arbejdsseddel knows exactly which physical roll off the shelf each "Moderrulle N" refers to. History (`saveToHistory`/`loadHistEntry`) round-trips kode/beskrivelse the same way as any other roll field, so reloading a saved calculation preserves the traceability.

**When the stock can't fully cover the order** (not a structural mismatch, just not enough of it — genuinely possible on a large order against a real, finite warehouse), the function returns `daekket: false` plus the specific `leftovers` from the last attempt; the whole stock list *does* get added to `#roll-list` in that case (grouped as above) — this is intentional, not a bug to "fix" by capping it: it's an honest reflection that the entire uploaded stock was tried and still came up short, and the operator needs to see the full picture to know what to source or produce more of.

## 4. Data flow

1. **User input** → `readRows()` parses roll rows and belt rows from the DOM into `{qty, b, l, srcRow, kode, beskrivelse}` objects (`kode`/`beskrivelse` are always empty strings for belt rows and for hand-typed roll rows — they're only non-empty for roll rows produced by the lagerliste auto-select, §3a), validating (integer qty ≥1, width/length >0), collecting per-row error strings; blank rows are silently skipped, partially-filled rows are hard errors.
2. `calculate()` reads buffer, `maxPerWidth`, `minRestW`, the optimization level, and the dorn settings object `{on, tillaeg, maxW, maxL}`, validates them, expands roll rows by quantity into `rollDefs` (one object per physical roll, carrying `kode`/`beskrivelse` along), and cross-validates every belt line fits the widest/longest available roll (else a specific error naming the offending line and the roll limits).
3. `_uid` (a module-level counter) is reset to 0 and the optimizer generator `optimerOpskaering({ rollDefs, bandRows, buffer, dorn, maxPerWidth, minRestW, niveau })` is started (it calls `buildUnits()`/`planCutting()` itself — §3b) and driven in chunks until it finishes or the user presses Stop.
4. The chosen plan has the shape `planCutting(rollDefs, units, maxPerWidth, S, ctx)` returns: `{ rolls, unusedRolls, leftovers, raw }` where each `roll` object is `{ idx, w, len, kode, beskrivelse, sections, usedLen, langRest? }`, each `section` is `{ len, cols, area, widthUsed, sideRest }`, each `col` (strip) is `{ w, items (units), filled, x, rest }`, and `raw` is the pre-stretch plan used by the optimizer's local search.
5. A sanity check compares `placedBands + lostBands` against `totalBands` and pushes an internal-consistency warning if they don't match (defensive check on the algorithm itself — should never fire; if it does, something in the packing broke).
6. `renderResult(d)` (`d` = `{ plan, buffer, dorn, maxPerWidth, minRestW, totalBands, placedBands, opt: { niveau, base, best, iterations, ms, stopped }, inputs }`; it adds `d.colors`, see §5a) builds the on-screen result: the optimization banner, an optional red "Manglende materiale" (missing material) card listing unplaced belts grouped by width/length (only if something didn't fit), then per-roll cards (stats + utilization bar, `renderRollCanvas` visualization, `sectionsHTML` table, each header appending `· <kode>` when the roll came from a lagerliste), a list of any completely untouched rolls, and a "Udskriv arbejdsseddel" print button. It also calls `saveToHistory(d)`. **There is no overall "Samlet overblik" summary card and no "Ordre / Reference" input card as of 15-09-2026** — both were removed on explicit request (the per-roll cards already carry every figure that overall card used to sum, and the order-reference fields added a card without adding calculation value); do not re-add either without being asked. `d` (and the history entry) accordingly no longer carries `orderRef`/`orderNote` — only very old `localStorage['opsk_history']` entries (saved before this date) may still have them, and the history-list rendering (`renderHistory`) still reads those two fields defensively for backward compatibility, falling back to a band-count title when absent.
7. **History**: `saveToHistory` snapshots `{id, v:3, date, time, inputs, summary}` into `localStorage['opsk_history']` (capped at 15, newest first) — `inputs.rolls[i]` includes `kode`/`beskrivelse` when present; since 24-09-2026 `inputs` also has `minRestW` and `niveau`, and `summary` has `waste` (shown as m² in the history line). `loadHistEntry` restores `minRestW`/`niveau` only when the entry has them — older entries leave the current field values alone. `entryInputs()` provides backward compatibility for older history entry shapes (`rollDefs`/`bandRows`/`bands` fields from earlier versions) so old saved calculations still load correctly (those never have kode/beskrivelse, which is fine — falsy just means no chip). Clicking a history item calls `loadHistEntry()` which repopulates every input field and rebuilds the roll/band row lists (kode/beskrivelse included, so the "Fra lager" chip survives a reload), then scrolls to top — it does **not** auto-recalculate.

## 5. Print/output behavior

Clicking **"Udskriv arbejdsseddel"** (`openPrintWindow(d)`) builds a complete standalone HTML document string (own `<style>` tailored for A4 portrait print, 12mm margins, page-break rules on sections/roll headers) reusing the same `sectionsHTML`/`describeColumn`/`piecesHTML` functions as the on-screen render (single source of truth — comment flags this deliberately). Content: header with title, roll count, buffer, dorn settings summary, min. restbredde (when set), an "Optimeret: spild X m² (−Y %)" note when the optimizer beat the baseline, date/time; the "manglende materiale" table if anything is unplaced; per-roll header line (dimensions + stats incl. spild m² + `· <kode>` when applicable), then **the roll drawing as a PNG** (`rollImageURL` renders `renderRollCanvas` off-screen at 680 px × dpr 2 in "Læsbar" mode and embeds it as a data URL, max 120 mm tall) with the same color legend as on screen, followed by the same row/strip/piece breakdown table as on screen (now with the per-size color chips; the print CSS sets `print-color-adjust: exact` so colors survive printing, and the hatching on waste plus the text in every cell keep it readable in black and white) (dorn rows highlighted, side-rest and length-rest rows shown in a muted italic style). It opens a new browser window (`window.open`), writes the HTML, and calls `w.print()` after a short delay (or on window load) — wrapped in try/catch since some browsers block/restrict `print()`. If the popup is blocked, an `alert()` tells the user to allow popups. No PDF/file is generated — it relies on the browser's native print dialog (print-to-PDF is up to the user).

## 5a. Tegning og interaktion (`renderRollCanvas`, `wireCanvas`, `setHighlight`)

`renderRollCanvas(canvas, roll, o)` (o = `{ W, mode: 'laesbar'|'skala', colors, highlight, dpr, buffer }`) is the single roll-drawing routine, used on screen (`drawRoll(ri)`), in the step mode (§5b) and for the print image (§5). It replaced v3.6's `drawRollCanvas`, whose beige `#EFEAE2` background and brown-grey text were leftovers from an old palette.
- **Colors per belt size** (`buildColorMap(d.inputs)` → `d.colors`, key `"<bredde>×<længde>"` via `sizeKey(u)`, which reads `u.bands[0]` so a dorn gets its belts' color): assigned in the order the sizes appear in the belt list, from `PALETTE` = blue `#2a78d6`, orange `#eb6834`, aqua `#1baf7a`, yellow `#eda100`, magenta `#e87ba4`, violet `#4a3aa7`. This order passed the dataviz skill's palette validator (every adjacent pair CVD ΔE ≥ 8 and normal-vision ΔE ≥ 15 on the light surface). Sizes 7–12 reuse the colors with a white **dot** texture, 13+ with a **diagonal line** texture (`tier` 1/2), so two sizes are never told apart by color alone. The same color appears as a `.chip` in the legend, before every piece in the plan table, in the step mode and on the printed sheet. Text on pieces is dark on light colors (yellow/pink/aqua) and white on dark ones (`inkOn`).
- **Marks:** 1.5 px surface gap between pieces/strips; dorn pieces get white vertical lines where they'll be split into belts, plus a lighter band for the kerf allowance; længderest and ordinary siderest are **hatched** (`getPatterns().waste`); a kept remnant (`roll.langRest`) is light green with a dashed green border and "Rest …"; an untouched tail is a green band "Rest som moderrulle: W × L mm". Transverse cuts are dashed steel lines. A left **ruler** shows the position (mm) at every transverse cut and `R1`, `R2`… per row; a width axis sits below.
- **Modes** (toggle `.seg-skala`, global `_skala`, remembered in `opsk_indstillinger.skala`): *Læsbar* (default) = v3.6's layout, every row at least 46 px so short rows stay legible, tail fixed at 46 px; *Målestok* = one uniform length scale for the whole roll length incl. tail/rest (body 320–680 px), so rows and remnant are in true proportion to each other. Width is always to scale; width and length are never on the same scale (a 20 m roll would be metres tall).
- **Hit regions:** every drawn piece/længderest/siderest/rest/tail is recorded in `canvas._hits` (px rect + mm data). `wireCanvas` shows a tooltip (`.vis-tip`: size, kap length incl. buffer, strip width, dorn split, position in the strip, knife positions) on hover **and on click/tap** (touch has no hover), and hovering highlights the strip. `setHighlight(ri, {si, ci})` is the single entry point for highlighting: it redraws the canvas with a dark outline plus a white inner line (visible on every palette color — an orange outline was invisible on orange pieces) and adds `.hl` to the matching table rows (`tr[data-ri][data-si][data-ci]`, `ci = 'rest'` for side-rest rows). Hovering a table row or section header (`wirePlanTable`) highlights in the drawing; clicking a strip in the drawing (non-touch devices) scrolls its table row into view and flashes it.

## 5b. Skæretilstand (`openStepMode`, `renderStep`)

A full-screen overlay (`#step-mode`) for a tablet/screen at the cutting table: one step per row (transverse cut) across all rolls, plus a final "Færdig" step. Each step shows (1) **the transverse cut** in large type with its position on the roll, (2) **the knife positions** for the longitudinal cuts, measured from the roll edge (`col.x + col.w` for every strip boundary that isn't the roll edge), plus the side-rest/kept-remnant width, (3) **each strip** with its pieces (same `piecesHTML` + color chips as the table), and the roll drawing with the current row highlighted (sticky beside the text on wide screens, above it on narrow ones). "Udført — næste →" marks the step done (green ✓ in the clickable step dots); "← Forrige", the arrow keys and Esc work too. The last step lists every roll's remnant to label and return to stock and any belts still missing material. Done-state lives only in memory.

**Responsive/touch (24-09-2026):** under 640 px the plan tables become stacked cards (strip no. / position / width on one line, content below), the stat grid is two columns, settings fields and action buttons go full width; on `(pointer: coarse)` inputs are 46 px tall with 16 px text (no iOS zoom), and delete/history buttons and the level selector get bigger touch targets.

## 6. Known quirks / gotchas

- **`_uid` is a global counter, reset to 0 at the top of every `calculate()` call (before the optimizer starts — never inside it, see §3b)** **and at the top of every `vaelgRullerFraLager()` call** — if any future refactor calls `buildUnits`/`explodeUnit` outside of one of these two entry points without resetting it first, unit IDs could collide with a stale `used` Set from a previous run. Currently safe because `used` sets are always freshly created per `fillColumn`/`fillSection` call, and — critically for `vaelgRullerFraLager` — the reset happens **once**, before its single `buildUnits()` call, and is *never* repeated between its many subsequent `planCutting()` calls in the same search (those all share the one persistent `units` array; resetting `_uid` again mid-search would let freshly-exploded temporary unit IDs collide with the real ones).
- **"Dorn" units retain their exploded `bands` array permanently** — even after packing, `netAreaOf` and all the descriptive/print functions iterate `u.bands` to know what's really inside a dorn bundle, rather than trusting `u.w`/`u.len` alone. Don't strip this array in any future edit.
- **Dorn viability check**: `perDorn = floor((dorn.maxW - dorn.tillaeg) / g.b)`; if the kerf allowance (`dorn.tillaeg`) alone is ≥ the effective max dorn width, `perDorn` naturally comes out < 2 and dorn packing silently disables for that group — but there's also an explicit UI warning for this exact case computed against `min(dorn.maxW, maxRollW)`.
- **Row length candidates are heuristically capped** (`CAND_LIMIT = 90`, subset-sum cap `CAP = 4000`) — for large/varied order sets this is an approximation, not an exhaustive search; it will not always find the mathematically optimal row length, just a good one from achievable lengths.
- **Retry/backoff only tries 5 rounds** (`planCutting`) and only reacts to belts that ended up in `leftovers`. Inefficient-but-complete plans are now handled by the optimizer (§3b), which is still a heuristic search — far better than the greedy baseline, but not a proof of global optimality. `vaelgRullerFraLager` (§3a) deliberately still uses the fast `GRUND` baseline only (it calls `planCutting` hundreds of times), so in rare cases it may pick one roll more than strictly necessary; the following `calculate()` then optimizes the plan on the chosen rolls.
- **Roll order is fixed by user input order**, not optimized — the algorithm never tries reordering rolls to find a better overall plan, per the explicit UI hint. This also applies to auto-selected rolls: they're inserted in the ascending-by-area order the search used, and the real `calculate()` run then consumes them in that same DOM order.
- **Merging identical-layout rows can run up to 3 iterations** interleaved with re-placing leftovers — if this ever needs a 4th pass for some edge case, it currently silently stops (bounded loop, not a fixed-point iteration to convergence).
- **History backward compatibility**: `entryInputs()` handles at least 3 different historical localStorage shapes (`v3` current `inputs` object, vs. legacy `rollDefs`/`bandRows`/`bands`) — do not remove this shim without checking whether users still have old entries in `localStorage`.
- **Internal consistency self-check** — a warning fires if `placedBands + lostBands !== totalBands`; this should be treated as a real bug indicator if it ever appears, not dismissed.
- **`maxPerWidth` interacting with leftovers** produces a specific warning suggesting the user raise/remove the limit — this is a UX hint, not an automatic retry without the constraint.
- **`vaelgRullerFraLager`'s worst case is genuinely slow-ish, by design, not a bug**: an order that turns out structurally impossible against the uploaded stock is caught early by the feasibility short-circuit (§3a) and returns instantly, but an order that's merely *short* on quantity/length (every constraint is individually satisfiable, there just isn't enough total stock) will exhaust the entire candidate list one `planCutting` call at a time before reporting the shortfall — this is now less likely to bite in practice than when the tool derived `antal` from a balance column (each Kode contributes at most 1 candidate roll now, so a real export's total candidate count is exactly its row count, not inflated by a computed multiplier), but the worst case is still bounded and was previously confirmed at ~300ms for a 974-roll/52-variant export before this change; keep the function button-triggered, not called in a loop or on every keystroke.
- **Stock quantity is never inferred, only counted in rows** (14-09-2026, see §3a) — if a warehouse genuinely holds more than one of a given Kode/size, that must show up as separate rows in the uploaded file. A maintainer tempted to "improve" this by re-deriving `antal` from some other BC column should not do so without being explicitly asked — the whole point of removing the previous balance-based derivation was that it could overstate real availability.
- **A tagged row's "Fra lager" chip is dropped the instant its Bredde or Længde is hand-edited** (the `input` listener added in `makeRow` for `cls === 'roll'` rows) — this is deliberate (the row no longer matches that stock item exactly) but means a maintainer debugging "why did the kode disappear" should check for this before assuming a bug.
- Field labels and all UI/print text are in **Danish** — variable/function names mix Danish domain terms (`dorn`, `moderrulle`, `bånd`, `strimler`, `tillæg`, `kaplængde`, `lager`) with English code structure; a maintainer unfamiliar with Danish should note: *moderrulle* = mother roll, *bånd* = belt, *dorn* = mandrel/bundle-packing mode, *strimmel/strimler* = strip(s), *kaplængde* = cut length, *tillæg* = allowance/addition, *skæretillæg* = cutting allowance (kerf), *siderest* = side leftover (unused width), *længderest* = length leftover, *lager* = stock/warehouse, *lagerliste* = stock list, *langRest* = the deliberately-kept long remnant introduced 15-09-2026 (see Step 6 in §3), distinct from *siderest*/*længderest* which are still ordinary waste.
- **Length beats width for leftovers, explicitly, since 15-09-2026** (see Step 6 in §3) — a maintainer used to the older "maximize the leftover's width" framing (still correct for every row *except* a roll's last one) should not "fix" the last row's stretched length back down to its own minimal content length; that would silently undo the explicit business rule and go back to leaving a short, less-reusable offcut plus a separate untouched tail. The **only** exception is the user's own "Min. restbredde" (since 24-09-2026): a remnant narrower than that is not kept, so the row is not stretched.
- **The stretch is part of the optimizer's objective.** The optimizer scores *finished* (stretched) plans, so it naturally prefers plans whose last row is narrow, or uses the full width (so the whole tail stays a full-width remnant) — intended, not a bug. Don't move the stretch into `placePass`/`attemptPlan`.
- **`GRUND` must keep reproducing v3.6** (§3). New ideas go behind a new `S` flag that is off in `GRUND`, and get added to `FASTE_STRATEGIER`/`tilfaeldigStrategi` — that keeps "never worse than the baseline" true by construction.
- **Plans in the optimizer share section objects** (local search keeps a prefix of the best plan's rows). Never mutate a section/column after it has been placed — create new ones (like `finishSection`, `mergeSameLayoutSections`, `mergeSubsetLayouts` and the non-mutating `forlaengSidsteRaekkeForLaengsteRest` do).
- **Settings in `localStorage['opsk_indstillinger']`** (`minRestW`, `niveau`, `skala`, `folds`) are per-browser conveniences only; everything works with defaults when storage is empty or blocked. Buffer and the other fields are still *not* remembered between visits (only via history) — unchanged, not asked for.
- **The settings cards start collapsed** (each shows its values in its summary line). If a user can't find a field, it's inside a folded card.
- **"Opskæringsplan" table text was deliberately shortened, 15-09-2026** (`describeColumn`, `piecesHTML`, `sectionsHTML`) — on explicit request to make the plan "mere overskuelig, ikke så meget tekst": `Kaplængde` → `Kap`, `(+350 buffer)` → `(+350)`, dorn's `Skær strimlen op i N bånd à W mm (skæretillæg X mm)` → `N bånd à W mm (tillæg X mm)`, `Enkeltbånd — kunne ikke pakkes på dorn` → `Enkeltbånd, ikke dorn`, the siderest/langrest table cell text dropped its repeated `W × L mm` (already shown in the row's own Bredde column and the section's own "Kap … mm" heading, so repeating it added nothing) down to just `Siderest, spild` / `Rest til senere brug`, the section title dropped the redundant `af moderrullen` suffix, the section's `sec-meta` line dropped repeating the sideRest width/label (already the next table row), and the table's last header changed from `Skal indeholde` to `Indhold`. All of this is purely cosmetic — none of it touches the numbers a plan actually reports (position, width, cut length, buffer, dorn belt count, længderest, the kept remnant's dimensions still shown in the per-roll stats card); don't reintroduce the longer phrasing without being asked, but do keep new lines added here just as short.
- **"Ordre / Reference" input card and the overall "Samlet overblik" summary card were removed, 15-09-2026** — on explicit request. `d.orderRef`/`d.orderNote` no longer exist anywhere in the live data flow (`calculate()` no longer reads `#order-ref`/`#order-note` — those elements no longer exist in the DOM at all — and `saveToHistory()` no longer writes the two fields); `renderHistory()`'s title/subtitle line still reads `e.orderRef`/`e.orderNote` defensively, purely so *old* `localStorage['opsk_history']` entries saved before this date keep showing their reference/note in the history list, falling back to a band-count title when absent (as it already did). Do not re-add either input card, and do not re-add the per-roll figures (bånd i alt, moderruller brugt, brugt rullelængde, samlet udnyttelse/spild) as a separate overall card without being asked — they're intentionally gone since the per-roll cards already carry the same information.
- **"Brug dorn-pakning" defaults to unchecked, 15-09-2026** (was checked by default before) — on explicit request. Nothing else about dorn packing changed; a returning user who wants dorn must now tick the box every time (or load a saved history entry that had it on — `loadHistEntry`'s `inp.dorn.on !== false` fallback logic for entries predating the `dorn` field is unrelated and untouched, still defaults *that* narrow legacy case to on).
